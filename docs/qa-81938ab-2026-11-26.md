## 3. 발견 목록

`확인함`에는 코드 흐름으로 확인한 결함도 포함합니다. 운영 서비스에 공격을 보내거나 사용자 PC에 입력을 주입해 재현하지는 않았습니다. 자원 소진처럼 실제 영향 규모를 확인하지 못한 것은 `그럴듯함`으로 구분했습니다.

1. **인증 전 연결 16개가 정상 에이전트의 재접속을 막습니다.**
   - 위치: `crates/hub/src/entry.rs:510`, 상한 정의 `entry.rs:30`.
   - 심각도: **보통**. 확신: **확인함 — 코드 흐름**.
   - 문제: 인증하지 않은 연결 수를 IP별로 나누지 않고 허브 전체에서 셉니다. 16개가 차면 모든 새 에이전트 연결에 429를 돌려줍니다.
   - 구체 상황: 외부 한 IP가 `/agent/ws` 16개를 열고 인증하지 않습니다. 90초가 되기 전에 연결을 순차 교체합니다. 약 11회/분으로 유지할 수 있어 IP별 60회/분 제한 안에 듭니다. 이때 다른 IP의 정상 에이전트도 재접속할 수 없습니다. 이미 인증된 연결까지 끊는다는 뜻은 아닙니다.
   - 최소 수정 방향: 인증 대기 상한을 IP별로 나눕니다. 인증 대기 시간을 짧게 제한합니다. 다른 IP의 정상 연결이 들어오는 시험이 필요합니다.

2. **여러 줄을 붙여넣으면 첫 줄 뒤 내용이 사라집니다.**
   - 위치: `crates/web/src/input.rs:375`, `input.rs:405`.
   - 심각도: **보통**. 확신: **확인함 — 코드 흐름**.
   - 문제: `text()`가 첫 줄바꿈 하나만 Enter 키로 바꿉니다. 남은 글은 `chars()`로 넘깁니다. `chars()`는 줄바꿈이 포함된 묶음 전체를 버립니다.
   - 구체 상황: 수정키를 누르지 않은 상태에서 숨은 입력칸에 `a\nb\nc`를 넣습니다. `a`와 첫 Enter만 전송합니다. `b\nc`는 전송하지 않습니다. 기존 시험은 줄바꿈 하나만 확인합니다.
   - 최소 수정 방향: 줄바꿈을 모두 순서대로 Enter 키로 변환합니다. 여러 줄 붙여넣기의 전송 결과를 비교하는 시험이 필요합니다.

3. **키를 놓는 입력이 거절돼도 눌린 키 장부에서 지웁니다.**
   - 위치: `crates/agent/src/platform/inject.rs:177`, `inject.rs:199`, `inject.rs:223`. 전송 결과 처리는 `inject.rs:120`.
   - 심각도: **보통**. 확신: **그럴듯함 — 실패 분기는 확인했으나 실제 키 고착은 재현하지 않음**.
   - 문제: 키·마우스 버튼 상태를 먼저 바꿉니다. `SendInput`이 0건을 돌려줘도 `input.blocked` 로그만 남깁니다. 놓기 실패를 상태에 반영하지 않습니다.
   - 구체 상황: 일반 화면에서 Ctrl 누르기는 성공합니다. 높은 권한의 창으로 전환된 동안 Ctrl 놓기가 거절됩니다. 장부에서는 Ctrl을 이미 지웠으므로 `release_all()`과 종료 처리도 다시 놓지 못합니다. 정상 화면으로 돌아온 뒤 Ctrl이 눌린 상태로 남을 수 있습니다.
   - 최소 수정 방향: 전송 결과를 호출부에 돌려줍니다. 실패한 놓기는 장부에 남겨 다음 놓기에서 다시 보냅니다.

4. **공개 카카오 토큰 입구가 본문을 제한 없이 읽습니다.**
   - 위치: `crates/hub/src/lib.rs:31`, `lib.rs:64`.
   - 심각도: **보통**. 확신: **그럴듯함 — 제한 누락은 확인했으나 자원 소진 부하 시험은 하지 않음**.
   - 문제: `client_id`를 검사하기 전에 `req.text()`로 본문 전체를 읽습니다. 이어서 폼 문자열을 다시 만듭니다. 이 공개 경로는 DO의 IP별 요청 제한을 거치지 않습니다.
   - 구체 상황: 인증 없는 외부 요청이 큰 POST 본문을 반복해 보냅니다. 잘못된 `client_id`라도 전체 본문을 먼저 메모리에 올립니다. 요청 본문에 비례한 메모리·처리 비용을 강제로 만들 수 있습니다. 플랫폼의 본문 상한이 실제 피해를 얼마나 줄이는지는 이번에 측정하지 않았습니다.
   - 최소 수정 방향: 읽기 전에 본문 상한을 검사합니다. 길이 헤더가 없는 요청도 읽는 동안 상한을 적용합니다. 공개 경로의 빈도 제한도 대조합니다.

5. **세션을 만든 뒤 브라우저 준비가 실패하면 허브 세션이 열린 채 남습니다.**
   - 위치: `crates/web/src/session.rs:125`, `session.rs:203`, `session.rs:211`, `session.rs:363`.
   - 심각도: **사소**. 확신: **확인함 — 코드 흐름**.
   - 문제: `/api/sessions` 성공 후 브라우저 연결 생성·offer 설정·허브 전송·answer 적용에서 실패하는 길이 허브에 `session.end`를 보내지 않습니다. 로컬 연결만 정리합니다.
   - 구체 상황: 세션 생성은 성공한 뒤 `create_offer()`가 실패합니다. 허브에는 종료 시각 없는 세션이 남습니다. 에이전트 도우미는 자체 시한까지 남을 수 있습니다. 같은 뷰어가 다시 열면 그 세션을 재사용하므로 접속 기록도 실패 시점에 끝나지 않습니다.
   - 최소 수정 방향: 생성된 세션의 실패 경로에서 해당 세션의 종료를 통지합니다. 다른 열기 요청이 같은 세션을 재사용 중인 경우는 기존 세대 검사와 함께 처리해야 합니다.

이전 연결의 늦은 사건이 새 연결을 종료한다는 의심도 검토했습니다. 연결 상태 처리기는 현재 연결의 상태를 다시 읽습니다. 따라서 옛 `failed` 사건만으로 새 연결을 종료한다는 주장은 근거가 부족해 발견 수에서 제외했습니다.

## 5. 검토 근거와 못 한 것

검토 기준은 `AGENTS.md`, `docs/goals.md`, `NEXT.md`, `03-prd.md`, `05-api-contract.md`, `decision-log.md`와 관련 SPEC입니다. 별도 볼트 인덱스나 그래프 질의 도구의 위치는 프로젝트 네비게이션에 없었습니다. 지정된 설계 문서를 읽고 import·호출 흐름으로 연결을 확인했습니다.

허브·앱, 에이전트, 웹·공유 계약을 나눠 읽기 전용으로 검토했습니다. Access JWT 검증, Ed25519 인증, 등록·설치·입장권, 세션·권한 요청 중계, 로컬 훅 입구, 입력 변환, 영상 처리 경로를 검토했습니다. 검토한 상수 값에서 PRD와의 불일치는 찾지 못했습니다. 잘린 권한 요청의 허용 금지는 웹과 에이전트 양쪽에 있습니다.

못 한 것:

- 헤드리스 핵심 흐름과 1440·390 화면 측정. Node·Wrangler·브라우저 자식 프로세스 생성이 `EPERM`으로 막혔습니다.
- 에이전트 통합 시험 6개. 실행 파일 실행 금지 지시 때문입니다. 사용자 에이전트와 `C:\ProgramData\WebDesktop`을 건드리지 않았습니다.
- ACL 실패의 일반 사용자 재현. 이번 제한 토큰에서의 실패만 확인했습니다.
- iPhone·iPad 실기기, LTE·TURN 실제 영상, 잠금·UAC, 사용자 입력 주입, 실제 Claude 대화형 훅. 사용자 PC에 영향을 주는 시험을 실행하지 않았습니다.
- 전체 시험의 80% 코드 커버리지. 계측하지 않았으므로 달성했다고 주장하지 않습니다.
